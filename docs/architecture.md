# Architecture and limits

Statify is an OMP extension that shortens eligible model-visible text, not user prompts or instruction messages. It leaves the main model unchanged. It starts off and defaults to Jev; Jeff is an explicit, experimental local provider. For setup and modes, see [Setup](setup.md) and [Local inference](local-inference.md#jeff-server); for measured results from the earlier `read`/`grep` Jev version, see [Benchmarks](benchmarks.md).

## Input flow

1. On `tool_result`, Statify considers text blocks from any tool, including shell and custom tools, and large error output. At the pre-model `context` hook it also considers earlier assistant messages containing only one plain-text block; changes there affect only the model request, not the stored conversation. User, developer, system, custom instruction, summary, image, thinking, and tool-call content is not rewritten. The extension cannot intercept every OMP input: tool definitions and system prompts are outside these hooks. It skips its own recovery tool, text blocks shorter than 4,000 UTF-16 characters, longer than 21,600, or needing more than 12 chunks. `skill://` and plan reads, requests for full output, and text or tasks matching its secret patterns bypass classification. Secret detection is heuristic, **not** a guarantee that sensitive data cannot leave the machine. OMP may already have truncated a result before Statify sees it. For mixed tool results, text blocks are treated independently and image blocks remain unchanged.
2. It splits eligible text into chunks of at most 1,800 UTF-16 characters, preferring a blank line before a top-level block in the last 400 characters of a chunk, then a nearby line break. It avoids splitting UTF-16 surrogate pairs; this is a conservative text heuristic, not an AST parser, and long blocks can still split. Structural boundaries can make a result under 21,600 characters exceed 12 chunks, in which case it passes through unchanged.
3. In `replace` or `shadow`, the selected provider receives the latest user task (up to 1,500 characters) and each eligible text chunk. Jev posts to OpenRouter's Decisions endpoint with model `typesafe/jev-1.13`; Jeff posts to the configured local `http://127.0.0.1:<port>/v1/systemone` with model `jeff-latest`. Jeff's URL is validated to require HTTP, exactly `127.0.0.1`, and an explicit port (1–65535); no remote URL is accepted for Jeff classification. The classification instructions and criteria are authored in English; user tasks and context text are not translated. The same parser requires a complete valid `noul` answer map; scores at or below 0.15 authorize omission **only in `replace`**, and uncertain chunks remain. Jeff's omission threshold is not validated for code/log relevance; explicit `shadow` makes no omission, but its default after enablement is `replace`. Missing or invalid answers, network failures, and processing errors leave the original text intact. The task is classification context, never rewritten in OMP.
4. In `replace`, the original extension-visible text is archived locally **before** the provider request. A successful replacement includes selected chunks, the original `read` path/hashline header when present, and a receipt listing exact shown and omitted ranges. Statify keeps the original instead if the receipt is not shorter in both UTF-16 characters and OMP's local `o200k_base` token count. That token count is a local estimate of main-model input, not actual billed usage; a Jev request may already have incurred a charge. An archive not used for a replacement is removed. `shadow` classifies but never replaces output or creates an archive.

## Modes, recovery, and privacy

Statify starts **off**, with provider `jev`. Selecting `/statify provider jeff` while off does not enable filtering; `/statify on` is still required. Both providers default to `replace` after enablement; Jev additionally needs an OpenRouter key (`statify.key`), whereas Jeff needs no OpenRouter key. `--statify-mode=shadow` and `--statify-mode=record` remain explicit choices for either provider; `record` sends nothing to either provider and never changes context. Removing a Jev key must not disable Jeff. A separate optional `statify-jeff.key` supplies Jeff's bearer token only when its server requires `JEFF_API_KEY`; it is not sent to Jev. Switching off affects subsequent requests, not an already-sent request. Jev sends no prompts or code to OpenRouter without explicit `on` and its key. When Jev is enabled, the latest task and eligible text **may leave the machine**; secret-pattern bypass is not comprehensive. In Jeff mode these classification task/chunk requests stay on loopback, never routed through OpenRouter; setup nevertheless contacts GitHub, PyPI/package hosts, and Hugging Face to download source, dependencies, and weights. Statify manages the [local Jeff server](local-inference.md#jeff-server) when enabled in `replace` or `shadow`. A [paired public-code benchmark](benchmarks.md#paired-jev--local-jeff-08b-relevance-and-latency) caught a necessary line omitted by Jeff 0.8B and an incorrect main-model answer; local recovery does not establish omission safety.

Jeff health checks use `/health`. If the server is unreachable or still loading, Statify bypasses classification and preserves the original without sending the task. Local decisions are serialized within the extension to avoid self-contention; other OMP processes can still return 529. A 503, 529, 422, timeout, network error, or invalid answer leaves the original intact. The 15-second per-request decision timeout is not a guarantee that a cold or contended server will respond in time. The existing secret bypass, archives, receipts, and token/character no-op checks apply to either provider.

The `/statify` native menu separates Jev and Jeff setup from enable/disable and statusline visibility. Main, Jev, Jeff, and connection-settings menus preserve the selected cursor after actions: the same label stays selected when available, otherwise the previous index is clamped; **Check connection** stays selected and its result remains visible. Keys use a dedicated masked input component, not ordinary chat; saving or canceling a key does not change enablement. Native enable actions check required setup and request explicit provider-specific consent. Jeff installation requires explicit approval to trust the installed plugin's `mise.toml` and run its existing pinned tasks; it changes neither provider nor enablement, but successful installation/update restarts the server if Jeff is already enabled. CLI/headless setup provides manual installation instructions followed by enablement for automatic serving.

New profiles show a compact themed statusline by default; persisted visibility choices are preserved. Its format is `<icon> Statify · Jev|Jeff · <segments>`, with active `●`, starting/loading/classifying `◐`, warning/error `!`, and off/record `○`. Priority is `off`, `invalid mode`, then `record`; these do not require credentials or a running server. Otherwise Jev can show `add key`; Jeff shows `server ready|loading|starting|stopped|failed|not installed` (a reachable external server appears ready), with `add Jeff key` when authentication requires a missing key. Requests in flight show `classifying`, or `classifying ×N` for multiple requests, instead of `replace`/`shadow`. In-flight accounting starts immediately before the provider HTTP request, after bypass checks and archiving; bypasses are ignored.

When Jeff is wanted (`enabled`, provider Jeff, mode `replace`/`shadow`) but not ready, its segment ends with `· paused`; managed startup includes elapsed seconds, refreshed by the one-second watcher. Examples:

```text
◐ Statify · Jeff · server starting 4s · paused
! Statify · Jeff · server stopped · paused
! Statify · Jeff · server failed · paused
! Statify · Jeff · not installed · paused
! Statify · Jeff · port 8765 busy · paused
● Statify · Jeff · server ready · replace · last −920 tok (493 used) · Σ −3.1k
```

After at least one completed provider request this session, enabled non-record statuslines show `last −<saved> tok` for a replacement, `last kept` for no-op/shadow, or `last error` for an API error. Every `last` segment appends `(<used> used)` when classifier input+output usage is known: for example, `last −1.6k tok (2.1k used)`, `last kept (493 used)`, or `last error (493 used)` when the provider returned usage. `Σ −<sessionSaved>` appears when positive. Saved tokens are the local estimate difference `countTokens(original) − countTokens(replacement)`, including the displayed receipt, not billed savings or classifier usage deducted from savings. Counts use integer, `k`, or `M` formatting (for example `920`, `1.6k`, `12k`). Session start resets stats; request completion, session/turn start, controls, and the startup watcher refresh the display. **Check connection** explicitly refreshes local health while idle.

Jeff supplies input-token usage and zero output tokens, so its completed requests show `(<used> used)` too.

## Managed Jeff lifecycle and diagnostics

Profile-scoped files live in `$PI_CODING_AGENT_DIR`, or `~/.omp/agent` by default: `statify-jeff-server.json` records `{pid, url, startedAt}`; `statify-jeff-server.log` captures managed stdout/stderr and is truncated at each start; `statify-jeff-setup.log` stores the installer transcript; and `statify-jeff-leases/<pid>` is an empty lease per live OMP process. Files use `0600`; the lease directory uses `0700`, without changing the profile directory's permissions. Installation is recognized by both `.venv` and `checkpoints/jeff-0.8b/model.safetensors` in `${JEFF_DIR:-$HOME/.local/share/omp-statify/jeff}`.

When enabled with provider Jeff in `replace` or `shadow`, session start and explicit enablement start `mise -C <plugin root> run jeff:serve` if health is unreachable, Jeff is installed, and no managed server is running. Managed starts set `JEFF_PORT` from the configured endpoint. Missing installation with no reachable server prevents enablement and directs the user to **Install / update Jeff**. Turn start refreshes health and stops a managed server when no longer wanted, including after CLI settings changes; it **never auto-starts or auto-restarts** the server. A crash can be retried by manual Start/Restart, explicit enablement, or a later session start.

Ownership requires both the recorded PID and its current `ps -o lstart=` value to match `startedAt`; dead or reused PIDs are treated as exited, never signaled. Starts are idempotent. Stop signals the owned detached process group with SIGTERM, waits up to five seconds, then escalates to SIGKILL and removes the record. Disablement or switching to Jev stops the managed server. Shutdown releases the OMP lease and removes dead-process leases; the last live OMP process stops the managed server. Reachable servers without a running ownership record are **external** and Statify never stops them, including foreground or LaunchAgent alternatives.

While Jeff is enabled, its menu offers Start, Stop, and Restart as applicable; `/statify jeff start|stop|restart|logs` provides direct controls. Manual Stop keeps Jeff selected and filtering enabled, but unavailable health keeps originals until the server is started again. After any start, one watcher checks health and refreshes status every second: ready triggers a notification; an exited process triggers a warning with the last five log lines, log path, and **Reinstall Jeff** suggestion; after 120 seconds it warns to open `/statify` → Jeff → Logs. It then stops watching, not the server. A signal stop can normally end the server log with `[jeff:serve] ERROR task failed`.

**Servers & ports** lists loopback Jeff servers by port with `ready`/`loading` and **this profile**/**external** labels; the current endpoint is checked and external process details are shown when available. Discovery probes loopback listeners and the configured endpoint; selecting a row connects, **Random free port** chooses an unused port and starts when enabled, and **Enter endpoint…** uses validated input. The submenu preserves its cursor. `/statify jeff servers` lists servers and `/statify jeff-url random` selects a free port in headless/RPC OMP too.

Endpoint changes save the URL. If it already serves Jeff, stop this profile's managed server on a different URL and connect without starting; otherwise restart a managed server from a different URL, or start if Jeff is wanted. Before managed startup, an occupied port with unreachable Jeff health prompts interactive users to choose a random free port, a discovered Jeff server, or cancel; automatic/headless startup warns and does not start.

**Reinstall Jeff** asks confirmation listing only `<jeffDir>/.venv` and `<jeffDir>/checkpoints/jeff-0.8b` and the approximately 2 GB re-download. Declining `Reinstall Jeff?` or the trust prompt leaves a running server untouched. After approval, it logs approval and stops the managed server only right before removing those two paths, runs normal pinned setup, and starts after success if Jeff is enabled. The action is available when installed or failed, directly after server controls when failed and otherwise after **Install / update Jeff**.

Every turn start and watcher tick caps the server log: above 1 MiB it is rewritten with `[statify: log trimmed at <ISO time>]` and the last 256 KiB starting at the next full line. The child writes in append mode so it continues after trimming; lines written during the rewrite may be lost. Cap errors are ignored.

The menu's **Logs** editor shows server and setup tails headed by their absolute paths; the direct logs command reports the last 20 lines and paths, and `/statify status` includes managed PID or external/stopped/failed/not-installed state and both log paths. The installer truncates its `0600` log per attempt, records timestamp/platform/plugin paths, preflight results, refusal, commands, sanitized stdout/stderr tails (at most 20,000 characters each), and exit/killed/error outcomes. Sanitization strips ANSI/control characters and redacts URL credentials, Bearer tokens, secret assignments, and environment secret values. Statify diagnostics never log keys. OMP JSONL logs under `~/.omp/logs/omp.<YYYY-MM-DD>.<pid>.log` include health failures and server start/stop/exit events. Setup failure notifications include the setup log path and suggest asking OMP “diagnose Statify Jeff setup”; the bundled [`statify-troubleshooting` skill](../skills/statify-troubleshooting/SKILL.md) guides safe diagnosis from these files and OMP logs.

## Recovery and cost limits

A replacement's receipt includes a UUID, SHA-256 hash, and 1-based inclusive **UTF-16 offsets in the archived text**, not source-file line numbers. `xd://statify_read` accepts that UUID and an inclusive range such as `1-2000`, returning exact archived text, up to 8,000 UTF-16 characters per call; a range must not split a surrogate pair. The ID resolves only within the current session's archive directory. File-backed sessions store archives beside the session file and can recover them when reopened; ephemeral-session archives are removed on shutdown. Recovery cannot retrieve content OMP removed before the extension ran. For omitted file content, an ordinary `read` of the relevant source-file ranges is another option when the file remains available; it is not a byte-for-byte snapshot guarantee if the file changed.
The recovery tool uses OMP's read-only approval tier. Its `xd://statify_read` write transport also bypasses Statify filtering, including for long recovered ranges.

OMP's `statify usage` log records status and numeric provider-reported input/output tokens and USD cost **when supplied**. Jev cost is only the Jev provider fee; Jeff reports tokens but no `usage.cost`, so `costUsd` is absent, **not $0 total local cost**. Compare provider data alongside main-model charges, local hardware/energy/operator cost, prompt-cache effects, latency, and rereads. A shorter result does not guarantee lower total cost or correct classification; omissions can hide important context despite the recovery path. Jeff's published benchmarks do not establish equivalence with Jev for task-conditioned code/log filtering; see [Jeff risks and remaining validation](jeff.md#risks-for-statifys-use) and [Benchmarks](benchmarks.md).

[Caveman Skill](https://github.com/JuliusBrussee/caveman/blob/main/skills/caveman/SKILL.md) is an optional, separate way to make an agent's *replies* brief; it does not compress `tool_result`, and Statify does not impose that writing style. Statify independently follows the useful principles of exact recovery and leaving already-sent conversation prefixes unchanged. It neither copies BSL-1.1 Caveman Engine/Proxy source nor claims verified Proxy integration with OMP; stacking a second compression layer could obscure recovery and needs separate testing.
